# Adaptive RAG: Routing, Grading, Rewriting, and Self-Correction

## Why Basic RAG Is Not Enough

A basic RAG pipeline retrieves the same way for every question: embed the query, fetch the top-k chunks, and generate. That works for straightforward factual questions, but it fails in predictable ways. A vague question retrieves vague chunks. A question about a topic the documents do not cover still gets an answer, because the model fills the gap with hallucinated text. A multi-part question needs several kinds of evidence, but a single retrieval pass returns only one slice. Adaptive RAG fixes this by making the pipeline inspect its own work and change strategy as it goes: route the query, grade what was retrieved, rewrite the query when retrieval is weak, and check the final answer against the sources before returning it.

## Query Routing

Query routing decides how a question should be handled before retrieval begins. A router — usually a small language model call or a classifier — looks at the question and picks a path. A factual question about the documents goes to the vector store. A question needing exact terms goes to hybrid search. A question that is out of scope, such as a general-knowledge question the documents cannot answer, can be routed to a direct answer or a polite refusal instead of wasting a retrieval round. A complex question can be routed to a decomposition step that splits it into sub-questions, each retrieved separately, with the results combined at the end. Routing is cheap compared to a full generation, and it prevents the most common failure mode in RAG: applying the same retrieval strategy to questions that need different ones.

## Relevance Grading and Query Rewriting

Relevance grading inspects each retrieved chunk and asks: does this chunk actually help answer the question? A grader, again usually a small model call, labels chunks as relevant or irrelevant, and irrelevant chunks are discarded before generation so they cannot distract the model or waste context. If too few chunks survive grading — or none at all — the pipeline does not give up: it rewrites the query. Query rewriting reformulates the question to match the language of the documents, for example expanding an abbreviation, adding synonyms, or turning a vague question into a specific one. The rewritten query is retrieved again, and the new chunks are graded. This retrieve-grade-rewrite loop repeats up to a fixed limit, typically two or three attempts, and then the pipeline proceeds with whatever it has — or admits it cannot answer.

## Self-Correction and Hallucination Checks

Self-correction is the final safety net. After the model drafts an answer, a grounding check compares every claim in the answer against the retrieved sources. One practical method is to split the answer into sentences and check whether each sentence shares evidence with at least one source chunk; a sentence with no supporting source is flagged as a possible hallucination. When the check fails, the pipeline can retry generation with stricter instructions, retrieve more context, or return the answer with a warning that parts of it are unsupported. A related check is answer relevance: does the answer actually address the question that was asked, or did the model drift into summarising the context? Together these checks turn RAG from a hopeful pipeline into an auditable one: every answer can be traced to its sources, every discarded chunk is recorded, and every rewrite is logged. That trace is what makes adaptive RAG trustworthy in production, where a confident wrong answer is worse than an honest "I don't know".
